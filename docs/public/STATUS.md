# 상태 판단과 검증 범위

## 상태는 무엇을 뜻하나요?

| 상태 | 판단 |
|---|---|
| 진행 중 | Orca가 실행 중이라고 명시적으로 보고한 작업 |
| 질문·승인 대기 | 입력·응답·승인을 기다린다는 신호가 있는 작업 |
| 완료 | 명시적 정상 완료 결과, 또는 Orca가 실제 관측한 Codex `Stop`·omp `agent_end`의 응답 턴 종료 |
| 오류 | 실패 결과가 명시적으로 확인된 작업 |
| 대기 | 에이전트가 없거나 취소·중단된 작업 |
| 확인 불가 | 상태 없음, 오래된 실행 신호, 지원하는 종료 증거가 없는 상태 |
| 미할당 | 해당 F키에 연결된 작업공간이 없음 |

한 작업공간에 여러 에이전트가 있으면 질문·오류·실행 중 같은 우선순위가 높은 상태를 모아 표시합니다. 실제 집계 규칙은 `orca_led/orca.py`와 테스트에 정의되어 있습니다. 작업 이름이나 터미널 문자열을 읽어 완료 여부를 추측하지 않습니다.

**완료는 응답 턴이 끝났다는 표시이며 작업 결과의 정확성이나 테스트 성공을 보장하지 않습니다.** Codex의 실제 `Stop`은 정상 결과 필드가 없어도 완료로 표시하며, 내부 진단에는 `completion_source: codex_stop`, `outcome_verified: false`로 구분합니다. 명시적 실패·취소·중단, 아직 실행 중인 하위 작업은 해당 상태를 우선 반영합니다.

**omp**도 같은 기준입니다. Orca가 omp 훅에서 직접 관측한 상태(훅 출처 기록이 있는 행)만 사용하며, 진행 중은 진행 중, 질문·승인 대기는 대기, 응답 턴 종료(`agent_end`)는 완료로 표시합니다. 이 완료 역시 결과의 정확성을 보장하지 않으며 진단에는 `completion_source: omp_agent_end`, `outcome_verified: false`로 구분합니다. 중단되었거나 세션 경계(새 세션 등)로 끝난 턴은 대기로 표시합니다. 진행 중·대기 상태는 마지막 훅 관측 후 30분이 지나면 확인 불가로 바뀌므로, 훅 없이 30분 넘게 걸리는 단일 도구 실행도 확인 불가로 보일 수 있습니다. 같은 Orca 훅 처리를 쓰는 pi·prime-agent는 Orca가 세션 시작만으로도 종료 상태를 만들 수 있어 지원하지 않으며 확인 불가로 표시합니다.

**확인 불가 조명은 Orca 연결이 정상이어도 나올 수 있습니다.** 실제 훅을 관측하지 못하거나 지원하는 종료 증거가 없으면 초록색으로 추정하지 않습니다. 터미널 제목으로 만든 상태와 복원 후 미확인 상태도 완료 증거로 사용하지 않습니다. 연결 오류는 앱의 연결 상태에서 별도로 확인해야 합니다. Codex 공유 서버의 칸별 알림 문제는 [사용 안내](USAGE.md#codex-응답이-끝났는데-핑크색이거나-다른-칸이-바뀌어요)를 참고하세요.

## Orca 버전과 화면 이동

어댑터는 Orca의 내부 API와 렌더러 구조를 사용합니다. 공개 확장 API에 기반한 장기 호환성은 보장하지 않습니다. 버전·실행 인스턴스·창·작업 순서를 확인하지 못하면 화면 이동을 중단합니다.

Orca 업데이트마다 바뀌는 렌더러 파일 이름과 내부 함수 이름은 고정하지 않습니다. 연동 프로그램이 설치된 `/Applications/Orca.app`의 `app.asar`를 읽기 전용으로 분석해, Cmd+숫자 단축키 처리 코드가 실제로 부르는 작업공간 순서 함수와 상태 저장소를 매번 찾습니다. 분석에 쓰는 파일은 Orca 앱의 무결성 기록과 일치해야 합니다. Orca 화면에서는 시작할 때 이미 불러온 모듈만 다시 참조하고, 찾은 함수의 소스가 그대로일 때만 호출합니다. 그 밖의 내부 함수를 시험 삼아 호출하지 않습니다.

| Orca 버전 상태 | LED 상태 표시 | F키 작업공간 이동·최소화 |
|---|---|---|
| **검증됨**: `orca_led/orca_compat.json`에 있는 버전 (현재 1.4.223) | 사용 | 사용 |
| **미검증**: 목록에 없지만 구조 분석과 화면 확인을 통과한 버전 | 사용 (메뉴에 `1.4.241 · 미검증`처럼 주황색 경고) | 꺼짐 |
| 구조 변경: 처리 코드를 찾지 못하거나 결과가 모호한 버전 | 중단 (`Orca 화면 구조가 바뀌어 읽을 수 없음`) | 꺼짐 |

Orca가 디스크에서 업데이트됐지만 아직 이전 버전이 실행 중이면 **Orca 재시작 필요**로 표시하고 읽지 않습니다. 새 버전을 검증하는 방법은 [설치 문서](INSTALL.md#orca-업데이트-후-버전-검증)에 있습니다.

순서는 Cmd+숫자 단축키가 쓰는 실제 작업공간 목록을 사용합니다. 일반 터미널 목록의 순서를 F키 번호로 간주하지 않습니다. 독립 폴더 작업공간, 원격 작업공간, 여러 창, 상태 신호가 없는 세션은 지원 범위가 제한됩니다. 모달 창이 열려 있거나 선택 대상이 바뀐 경우에도 이동을 보류할 수 있습니다.

## 확인한 것과 남은 것

| 항목 | 검증 상태 |
|---|---|
| 기본 USB LED 패킷, 상태 읽기 | 실제 기기에서 확인 |
| 기본 Bluetooth LED 표시 | 실제 기기에서 육안 확인 |
| Bluetooth F키로 작업공간 이동·같은 키 최소화 | 실제 사용자가 확인 |
| Keychron 공식 키코드 순서(Command·Option·Mission Control·Launchpad 등) | 빌드 시 정적 검사, 컴파일된 키맵과 설치 후 읽은 키맵의 사용자 정의 키가 공식 펌웨어 키맵과 일치 |
| 호스트·C 펌웨어·복원 도구의 오류 처리 | 자동 검사 대상 |
| Codex 0.160.0 실제 완료 신호 → F11 상태 | `--no-daemon`으로 기존 대화를 재개하고 실제 Stop → `complete` 판정 확인; 물리 LED는 확인 대기 |
| omp 실제 훅 → 작업공간 상태 | Orca 1.4.241에서 실행 중인 omp 세션의 훅 행 → `running` 판정 확인; 완료·물리 LED는 확인 대기 |
| 모든 F1–F12 키의 모든 실기 조합 | 미완료 |
| 테마 펌웨어 설치·USB 지원 응답 | Launcher로 최신화한 공식 펌웨어 위에 실제 설치, 쓰기 내용 읽기 일치, `theme_protocol=2` 확인 |
| 설치 후 일반 키 실제 입력 | 확인 대기 |
| 설치 전후 키맵·매크로·레이아웃·조명 | 각각 두 번 읽고 비교: 사용자 정의 키는 동일, 일부 키·조명은 기본값으로 초기화 |
| 설치된 설정 앱의 색상 편집·취소 | 실제 GUI에서 입력·취소 후 원래 색상 복귀 확인 |
| 설정 앱에서 저장한 테마의 Bluetooth 표시 | 청록색·계속 켜짐으로 저장한 설정의 실제 표시를 사용자가 확인 |
| 새 테마 적용 후 F키 이동·최소화 | 사용자가 F1 이동·같은 키 최소화 정상 확인 |
| 장시간 연결, 배터리 영향, 잠자기·깨우기 | 추가 실기 확인 필요 |

새 테마 실기에서는 설정 앱에서 확인 불가 상태를 청록색 `#00FFFF`·계속 켜짐으로 바꿔 저장했습니다. 사용자가 무선 LED 표시와 F1 작업공간 이동·같은 키 최소화가 모두 정상이라고 확인했습니다. 이 결과는 해당 시험 조합의 확인이며 모든 색상·효과·물리 키 조합의 검증을 뜻하지 않습니다.

기본 Bluetooth 전송의 150ms 신호 / 100ms 구분 간격에서 전체 상태가 약 9초, 한 칸 변경이 약 4초 걸렸습니다. 전체 테마 적용에는 약 2분을 예상합니다. Bluetooth에는 수신 확인 응답이 없으므로, macOS가 쓰기를 수락했다는 결과만으로 키보드가 실제로 반영했다고 판단할 수 없습니다.

## 설정 보관과 연결 만료

설정 앱은 `runtime/theme.json`에 테마를 보관합니다. 이 파일은 공개 저장소에서 제외합니다. 펌웨어의 테마는 RAM에만 적용되어 키보드 전원을 끄면 기본값으로 돌아갑니다. 재연결 시 연동 앱이 저장한 설정을 다시 전달합니다.

상태 명령은 EEPROM에 쓰지 않습니다. 마지막 유효 상태 갱신으로부터 15초 후 키보드는 화면 이동 기능을 해제하고, 30초 후 원래 조명으로 돌아갑니다. 정상 중지는 즉시 해제 명령 전송을 시도합니다.
